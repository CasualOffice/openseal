From upload to sealed PDF.

Four moves for the sender and the signers. The evidence is assembled for you at every step.

  1. {{icon:file-up:24}}

    Upload

    Bring a PDF. Scripts, actions and embedded files are stripped before anyone sees it.

  2. {{icon:pen-line:24}}

    Place fields

    Signature, initials, date, text, checkbox and more, dropped on the page or found from text tags.

  3. {{icon:signature:24}}

    Sign

    Each signer is invited in turn, authenticates, consents and signs on any device.

  4. {{icon:stamp:24}}

    Seal

    A PAdES seal with a trusted timestamp, a certificate of completion and the audit trail inside the PDF.

{{icon:shield-check:16}}Evidence first

Proof that outlives the platform.

A completed agreement shows which document every party saw, who signed it, when and how. Anyone can check that for decades, with no account and no server.

  • {{icon:stamp}}PAdES B-T by default, up to B-LTASealed as an incremental update with an RFC 3161 timestamp. Long-term validation and archive renewal are one setting away.
  • {{icon:link}}Hash-chained audit trailEvery event is canonical JSON (RFC 8785) linked by SHA-256 to the one before it. Deleting, inserting, reordering or editing any event is detected.
  • {{icon:badge-check}}Checked by independent validatorsOur verifier, pyHanko and EU DSS must agree on every sealed and tampered fixture; all 417 admissible PDFs of a 422-file real-world corpus pass all three.
  • {{icon:key-round}}Keys in your HSMSeals are made by keyd, a separate daemon that holds the key behind PKCS#11 and signs digests, never documents. Cloud KMS backends are planned.
  • {{icon:shield}}Every upload treated as hostileA bounded PDF reader, fuzzed for 24 hours per entry point, rewrites the file without active content before it is signed.

Your servers, your keys, your data.

One command builds and starts the whole stack on a machine with Docker. Nothing calls home.

  • {{icon:server:16}}server: the API, the signing ceremony and the web app
  • {{icon:workflow:16}}worker: email, reminders, sealing and webhooks
  • {{icon:key-round:16}}keyd: the seal key behind PKCS#11, over mutual TLS
  • {{icon:database:16}}PostgreSQL: row-level security per account
  • {{icon:package:16}}S3-compatible store: write-once documents
  • {{icon:clock:16}}Timestamp authority: a development TSA, or yours

Self-hosting guide{{icon:arrow-right:16}}

# Build and start everything
git clone https://github.com/CasualOffice/openseal
cd openseal
docker compose up -d --build --wait

# Create the first account and administrator
docker compose exec \
  -e OPENSEAL_ADMIN_PASSWORD='a long passphrase' \
  server casual-sign-server bootstrap \
  "Acme" admin@acme.example "Ada Admin"

# Web app  http://localhost:8080
# Mail     http://localhost:8025

Questions people ask.

More in the documentation FAQ.

Can I use it for real agreements today?{{icon:chevron-down}}

Not yet. OpenSeal is pre-alpha: the engine is complete and tested, and the server and web app run end to end on Docker Compose, but the release gates (an external security review, an accessibility audit, validation in Adobe Acrobat and a counsel review) are still ahead. The roadmap shows what is left for Release 1.

Are the signatures legally binding?{{icon:chevron-down}}

OpenSeal is designed to support electronic-signature laws such as ESIGN, UETA and eIDAS. Whether a given signature is valid depends on your deployment, its configuration, the jurisdiction and the transaction. Nothing here is legal advice.

How do I check a document without your servers?{{icon:chevron-down}}

Open the verify page from any OpenSeal install, or run it locally; the check runs in your browser and the file stays on your machine. The seal is standard PAdES, so independent tools such as pyHanko and EU DSS validate it too.

Can I build a commercial product on it?{{icon:chevron-down}}

Yes. Apache-2.0 allows commercial and proprietary use, embedding, hosting and resale. When you redistribute it, keep the LICENSE and the NOTICE file. See brand and attribution.

Does it have an API and webhooks?{{icon:chevron-down}}

Yes: a REST API under /api/v1 with API keys and OAuth client credentials, idempotency keys, ETags, and webhooks signed with the Standard Webhooks scheme. Read the API reference.

Where are the signing keys?{{icon:chevron-down}}

In a separate service, keyd, which talks PKCS#11 to your HSM (SoftHSM in the development stack) and signs digests only. File keys are refused outside development.

Run it on your machine in one command.

Docker Compose brings up the server, the worker, the key service, the database, storage, a mail catcher and a timestamp authority.
