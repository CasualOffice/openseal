Self-hosting and configuration

OpenSeal is built to run on your infrastructure. The single-node Docker Compose stack is for evaluation and development today; this page explains its parts, how they are configured, and what a production deployment needs.

{{icon:triangle-alert}}

OpenSeal is pre-alpha. The Compose stack generates its own keys and certificate authority and sends cookies over plain HTTP. It is not a production deployment, and the production checklist below is guidance for when the release gates have passed. A Helm chart and a high-availability reference are planned (VS-20).

Every image is pinned by digest. Nothing secret is baked into an image.

Configuration

Everything is configured through environment variables, and every secret can instead be given as a file with NAME_FILE; setting both is an error. The server reads:

VariableWhat
OPENSEAL_DATABASE_URLPostgreSQL connection for the application role
OPENSEAL_MIGRATE_DATABASE_URLConnection for the schema owner, used by migrate
OPENSEAL_JWT_SIGNING_KEYThe key that signs API access tokens
OPENSEAL_BLOB_DIR or OPENSEAL_S3_*Where documents are stored: a directory, or an S3-compatible bucket
OPENSEAL_PUBLIC_URLThe address recipients and integrators use; must be HTTPS in production
OPENSEAL_LISTENThe address and port to listen on
OPENSEAL_TRUSTED_PROXIESProxies whose forwarded client address is believed, for the evidence's IP addresses
OPENSEAL_GEOIP_DBOptional GeoIP database for the approximate location in the certificate
OPENSEAL_WEBAPP_DIRThe web app's files, served at /
OPENSEAL_WEBHOOK_ALLOWWorker: address ranges webhooks may reach although private (refused by default)

Each binary's module documentation lists all of its variables (server/casual-sign-server/src/main.rs, -worker, -keyd), and docker-compose.yml sets every one of them. Ports in the Compose file bind to 127.0.0.1; OPENSEAL_HTTP_PORT and OPENSEAL_MAIL_PORT move them.

Production checklist

AreaDo
Signing keyA document-signing certificate from a CA your relying parties trust (for example an AATL member, or a qualified seal certificate for eIDAS), with its key generated in your HSM; configure keyd with PKCS#11. Never a file key.
TimestampsAt least two RFC 3161 timestamp authorities with a service level (qualified, if you need eIDAS qualified time)
EmailA sending domain with SPF, DKIM and DMARC (p=quarantine or stricter); an SMTP relay or provider; bounce handling
DatabasePostgreSQL 15 or later, encrypted, with point-in-time recovery; a separate role for migrations
Object storeS3-compatible, with versioning and encryption; Object Lock in compliance mode for regulated tenants
EdgeTLS 1.2 or later (1.3 preferred), HSTS, and a web application firewall if you have one
TrustYour organization's roots for verification; the EU trusted list if you verify EU signatures
Consumer disclosureHave counsel review the electronic records disclosure for your jurisdictions before sending to consumers
ObservabilityAlert on seal failures, timestamp failover, email bounce rate and job backlog
RetentionDecide retention before go-live and record it in your records schedule

Upgrades

Migrations are forward-only and numbered. They are designed to stay compatible for one release, so old and new nodes can run side by side during a rolling deploy. Do not skip a minor version without reading its release notes.

Backups

Back up PostgreSQL and the object store together: the database holds the record and the audit chain, the store holds the documents they point to. The secrets volume of a development stack holds its keys; a production seal key lives in the HSM and is backed up the HSM's way.
