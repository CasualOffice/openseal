Contributing

OpenSeal is built in the open, and contributions are welcome. Because evidence integrity is the product's most critical property, the bar for changes that read, write or sign a PDF is high, and every rule below has a reason.

Get the code running

You need Rust 1.96 (pinned in rust-toolchain.toml), Python 3.12, and Docker for the validators and the full stack.

git clone https://github.com/CasualOffice/openseal && cd openseal
git config core.hooksPath .githooks          # once per clone: repository checks and commit messages
cargo test --workspace                       # every crate's tests
python3 -I fixtures/tools/generate.py        # the hostile PDF set
tools/ci-local.sh                            # everything CI runs, locally

The web app needs no build step: python3 -I tools/serve-webapp.py, then open http://127.0.0.1:8130/app.html?mock=1. Its browser tests are in webapp/e2e (Playwright and axe).

Before you write code

  • Every piece of work has a row in the tracker, docs/14. The only roadmap is docs/06.
  • The design is written down in a numbered document. Decisions that need one have an accepted ADR in docs/08.
  • Name the acceptance test first. A test counts only if it was seen to fail without the change.
  • Open an issue to discuss anything substantial.

Rules that protect the evidence

  • Untrusted input never panics. No unwrap, expect, indexing or unchecked arithmetic on values from a file or a request; return a typed error with a stable code.
  • Every parser is bounded, with each limit named, a hostile fixture and a fuzz target.
  • A sealed document is never modified; later changes are signed incremental updates.
  • The audit trail is append-only; corrections are new events.
  • Our verifier is never enough alone: anything that seals is checked by pyHanko and EU DSS too.
  • Time, randomness and keys are supplied, never sampled by an engine crate; the same input gives the same bytes. No unsafe in crates/.
  • Cryptography is never hand-rolled.
  • No personal data, real agreements or private keys in fixtures, logs or commits.

Clean room

Never copy, translate or adapt code, schemas, CSS, interface text or tests from AGPL projects (Documenso, DocuSeal, OpenSign Labs' OpenSign, LibreSign) or from vendors' documentation. Ideas from their public documentation and behaviour are fine. Sign off every commit under the Developer Certificate of Origin (git commit -s); for this project the sign-off also attests that no such material is included.

Commits

Conventional Commits, one coherent change per commit, citing the tracker id and giving the reason:

feat(seal): compute the signature placeholder from the chain and timestamp (T-1G)

A change is not done until every document it affects is true in the same commit. Never skip the hooks.

Security issues

Do not open a public issue for a vulnerability, a malicious PDF or a forgery technique. Follow the security policy.
