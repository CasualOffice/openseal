API reference

The OpenSeal API is a JSON REST API over HTTPS. Everything the web app does, it does through this API: public operations, from creating and sending an envelope to reading its sealed documents and audit trail.

{{icon:triangle-alert}}

Pre-release. The contract is version and may still change before 1.0. OpenSeal v0.1.0 is for evaluation, not yet for production agreements.

Base URL

Every deployment serves the API at its own address, the OPENSEAL_PUBLIC_URL its operator configures (see Configuration). Operations live under /api/v1; discovery documents under /.well-known/. The examples on these pages use https://sign.example.com.

  • Request and response bodies are JSON (application/json); a JSON body sent as anything else is refused 415.
  • Times are RFC 3339 in UTC; ids are UUIDv7 strings.
  • Every response carries X-Request-Id; quote it when you report a problem.
  • An object of another account answers exactly as one that does not exist: 404 CS-API-0002.

Your first request

curl https://sign.example.com/api/v1/envelopes?limit=5 \
  -H "Authorization: Bearer $OPENSEAL_API_KEY"

Authentication

Every operation except the public ones (sign-in, the token endpoint, discovery) needs a credential. Integrations send it as a bearer token:

Authorization: Bearer <API key or access token>

A credential belongs to one workspace and acts as one member. It holds at most the permissions of that member's profile, narrowed by its own scopes, and it is checked again on every request: a revoked key, an expired token or a removed member is refused on the next call.

MethodUse it forCredential
API keyScripts and server-side integrations of your own workspaceosk_…, scoped, optionally expiring, shown once

API keys

An administrator creates a key in the web app (Admin, API) or with Create API client (kind: "api_key"). The key is osk_ followed by 256 random bits; OpenSeal stores only its SHA-256, so it is shown once, in the response that creates it. Keys of a sandbox workspace start osk_test_.

# Create a key (as an administrator), then use it
curl -X POST https://sign.example.com/api/v1/api-clients \
  -H "Authorization: Bearer $ADMIN_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "CRM sync", "kind": "api_key", "scopes": ["envelopes:read", "envelopes:write"], "expires_in_days": 90}'

curl https://sign.example.com/api/v1/envelopes \
  -H "Authorization: Bearer osk_3f9a6c1e8b2d4f7a9c0e5b1d3f6a8c2e"

OAuth 2.1: authorization code with PKCE

For an app that acts for members of a workspace. Register it with kind: "oauth_app" and its redirect_uris (https://, or http:// to a loopback address); it gets a client_id and a client_secret. OpenSeal accepts confidential clients only: the app authenticates at the token endpoint with its secret and sends a PKCE verifier (S256).

  1. Send the member to the authorization endpoint with a fresh PKCE challenge and state. OpenSeal signs them in if needed and asks for consent.

    https://sign.example.com/api/v1/oauth/authorize?response_type=code
  &client_id=CLIENT_ID&redirect_uri=https%3A%2F%2Fapp.example.com%2Fcallback
  &scope=envelopes%3Aread%20envelopes%3Asend&state=STATE
  &code_challenge=CHALLENGE&code_challenge_method=S256

  2. Receive the redirect. On consent the member's browser returns to your redirect URI with code, your state (check it) and iss (RFC 9207). A code lasts ten minutes and works once.

  3. Exchange the code with your client credentials and the verifier:

    curl -X POST https://sign.example.com/api/v1/oauth/token \
  -u "$CLIENT_ID:$CLIENT_SECRET" \
  -d grant_type=authorization_code \
  -d code="$CODE" \
  -d redirect_uri=https://app.example.com/callback \
  -d code_verifier="$VERIFIER"
    {
  "access_token": "eyJhbGciOiJFUzI1NiJ9…",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "envelopes:read envelopes:send",
  "refresh_token": "osr_…"
}

  4. Refresh before the hour is up with grant_type=refresh_token. Each refresh token works once and is replaced; one used twice revokes the whole family, so store the new one every time.

The SDKs do steps 1 and 3 for you:

// TypeScript
const { url, verifier, state } = await os.authorizationUrl({ clientId, redirectUri, scope: "envelopes:read envelopes:send" });
// … redirect to url, then on the callback:
await os.token({ clientId, clientSecret, grant_type: "authorization_code", code, redirect_uri: redirectUri, code_verifier: verifier });
# Python
url, verifier, state = client.authorization_url(client_id, redirect_uri, "envelopes:read envelopes:send")
client.token(client_id=client_id, client_secret=client_secret, grant_type="authorization_code",
             code=code, redirect_uri=redirect_uri, code_verifier=verifier)

Members see and withdraw the apps they consented to under Connected apps; withdrawing revokes the refresh tokens at once and the access tokens on their next request.

OAuth client credentials

An OAuth app can also take a token for itself, acting as its owner:

curl -X POST https://sign.example.com/api/v1/oauth/token \
  -u "$CLIENT_ID:$CLIENT_SECRET" \
  -d grant_type=client_credentials \
  -d scope="envelopes:read"

JWT bearer grant

For a server that acts for a member without a browser each time, as DocuSign's JWT grant does. Register a kind: "jwt_integration" client with your public_key (PEM, EC P-256 or RSA; never send the private key). The member consents once, through the same authorization URL as above. Then your server signs an assertion with its private key and exchanges it:

{
  "iss": "CLIENT_ID",                       // the integration's client id
  "sub": "USER_ID",                         // the member who consented
  "aud": "https://sign.example.com",        // the public URL, or the token endpoint's
  "iat": 1763631000,
  "exp": 1763634600,                        // in the future, at most an hour after iat
  "scope": "envelopes:read envelopes:send"  // optional; within the consent
}
# Python, with any JWT library (PyJWT shown) for the assertion
assertion = jwt.encode(claims, private_key_pem, algorithm="ES256")
token = client.token(assertion=assertion)        # grant_type is set for you
curl -X POST https://sign.example.com/api/v1/oauth/token \
  -d grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer \
  -d assertion="$ASSERTION"

A member who has not consented gets invalid_grant with CS-AUTH-0005; a bad signature, audience or lifetime gets invalid_grant with CS-AUTH-0014. No refresh token is issued: sign a new assertion when the hour is up.

Access tokens

Access tokens are ES256 JWTs (issuer the public URL, audience openseal-api) valid for one hour. The keys that verify them are at /.well-known/jwks.json; the server's OAuth metadata (RFC 8414) is at /.well-known/oauth-authorization-server. Token endpoint errors follow RFC 6749 (invalid_client, invalid_grant, invalid_scope, unsupported_grant_type) with OpenSeal's code in error_description.

Scopes and permissions

Each operation names the permission it needs (on its page, under Permission). A key or token holds the permissions its scopes cover, and never more than its member's profile allows:

Errors

Every error is an RFC 9457 problem (application/problem+json) with a stable code, never reused, that you can branch on. errors[] points at the members that are wrong with JSON pointers. Messages never contain document text or personal data.

HTTP/1.1 422 Unprocessable Entity
Content-Type: application/problem+json

{
  "type": "urn:openseal:problem:CS-API-0001",
  "title": "Malformed or invalid request",
  "status": 422,
  "code": "CS-API-0001",
  "detail": "subject is longer than 255 characters",
  "request_id": "0193d3a1-5b7c-7e2f-9a41-6c8d2e0f3b15",
  "errors": [{ "pointer": "/subject", "code": "CS-API-0001" }]
}

The SDKs raise these as OpenSealError with code, status, requestId (request_id in Python) and errors.

Pagination

Lists are cursor-paginated and stay stable while new objects arrive. Ask for up to limit items (1 to 200, default 50); the answer has items and next_cursor. Pass next_cursor back as cursor until it is null. A cursor belongs to the sort and order it was issued for.

curl "https://sign.example.com/api/v1/envelopes?limit=50&status=sent" -H "Authorization: Bearer $OPENSEAL_API_KEY"

{ "items": [ { "id": "0193…", "status": "sent", "subject": "Please sign: Mutual NDA" } ],
  "next_cursor": "eyJpZCI6IjAxOTMifQ" }

curl "https://sign.example.com/api/v1/envelopes?limit=50&status=sent&cursor=eyJpZCI6IjAxOTMifQ" -H "Authorization: Bearer $OPENSEAL_API_KEY"

Idempotency

Every POST accepts an Idempotency-Key (1 to 255 printable ASCII characters). Retrying with the same key and body within 24 hours returns the first response, marked Idempotency-Replayed: true, and does the work once: a network failure while creating or sending an envelope never sends it twice.

  • The same key with a different body: 409 CS-API-0004.
  • The first request still running: 409 CS-API-0011; retry shortly.
  • A response that held a secret (a new API key) is not stored; its replay answers 409 CS-API-0009.
curl -X POST https://sign.example.com/api/v1/envelopes/$ID/send \
  -H "Authorization: Bearer $OPENSEAL_API_KEY" \
  -H "Idempotency-Key: send-order-1042"

Versions, ETags and If-Match

Envelopes, and templates, have a version that every change raises. Reads return it as ETag: "v<version>". Changing or deleting a draft envelope, its recipients, fields or documents, and opening a correction, require If-Match with the version you read, so two editors never overwrite each other:

curl -X PATCH https://sign.example.com/api/v1/envelopes/$ID \
  -H "Authorization: Bearer $OPENSEAL_API_KEY" \
  -H 'If-Match: "v3"' \
  -H "Content-Type: application/json" \
  -d '{"subject": "Please sign: Mutual NDA (revised)"}'

A stale version answers 412 CS-WF-0002: read the envelope again and reapply your change. No If-Match where one is required answers 428 CS-API-0008.

Rate limits and request limits

Requests are limited per credential, per signing link, per client address and per sign-in name. Responses carry RateLimit and RateLimit-Policy (the IETF draft headers); a refused request answers 429 CS-API-0003 with Retry-After in seconds. Back off and retry after it, keeping the same Idempotency-Key.

Every limit, with its error code, is in the limits register; an operation with limits of its own lists them on its page.

Versioning

The version is in the path: /api/v1. Within a version changes are additive only: new operations, new optional parameters, new members in responses and new event types. Clients must ignore members they do not know. A breaking change gets a new path (/api/v2), and the old version is kept for twelve months alongside it. The changelog records every change. Until 1.0 the contract () may still change.

Webhooks

Subscribe a URL with Create webhook to receive events such as envelope.completed as they happen. Each delivery is a POST of a small JSON event (ids and status, never names, addresses or documents: fetch those with your credential):

{
  "id": "0193b2f4-7c1e-7b3d-8e45-1f2a3b4c5d6e",
  "type": "envelope.completed",
  "created_at": "2026-11-20T09:30:00Z",
  "account_id": "0193a0c2-…",
  "data": { "envelope_id": "0193…", "status": "completed", "version": 7 }
}

Deliveries are signed with the Standard Webhooks scheme: webhook-id, webhook-timestamp and webhook-signature (v1, and the base64 HMAC-SHA256 of id.timestamp.body under your whsec_… secret). Verify the raw body before parsing it, and refuse a timestamp more than five minutes away:

// TypeScript
import { verifyWebhook } from "@openseal/sdk";
const event = await verifyWebhook(process.env.OPENSEAL_WEBHOOK_SECRET, request.headers, rawBody);
# Python
from openseal import verify_webhook
event = verify_webhook(os.environ["OPENSEAL_WEBHOOK_SECRET"], request.headers, raw_body)

Delivery is at least once: answer 2xx within 10 seconds, and deduplicate on webhook-id. Failures are retried with exponential back-off for 15 attempts, about three days, and each attempt is in the delivery log. Order is not guaranteed; use data.version to discard stale events. URLs must be HTTPS to a public address. The Webhooks guide lists every event type and covers secret rotation.

Sandbox

Build and test against a sandbox workspace. An organization administrator creates one in Organization settings, Workspaces ("Sandbox workspace"), or with sandbox: true on Create organization workspace; a workspace is a sandbox for good. In a sandbox:

  • API keys start osk_test_ and authenticate the same way;
  • envelopes are sealed with a separate test key whose certificate says it is not for agreements, and the signing page, emails and certificate say it is a test;
  • nothing is counted against plan quotas.

Every workspace answers sandbox in Get account, so your integration can check where it is.
