FAQ

Short answers, with links to the longer ones.

Status

Is OpenSeal ready for production?

No. It is pre-alpha. The PDF and evidence engine is complete and tested against 422 real-world PDFs and a set of hostile files; the server, worker, key service and web app run end to end on Docker Compose, and v0.0.1, the first pre-release, is published for evaluation. The gates before a preview (an external security review, an accessibility audit, validation in Adobe Acrobat, a licence review and a counsel review) are still ahead. The roadmap shows where things stand.

When will version 1.0 be released?

The project does not promise dates. Work is sized and ordered in the roadmap, and 1.0 is reached when its slices and release gates are done.

Legal

Are signatures made with OpenSeal legally binding?

OpenSeal is designed to support electronic-signature laws such as ESIGN and UETA in the United States and eIDAS in the European Union. Whether a particular signature is valid depends on the deployment, its configuration, the jurisdiction and the transaction. Nothing on this site is legal advice; ask counsel for your case.

Is it certified for SOC 2, ISO 27001 or 21 CFR Part 11?

No. A self-hosted deployment is certified by its operator, not by the software. OpenSeal plans control mappings to help operators (LEG-04) and a Part 11 mode (VS-19); neither is a certification.

Does it support qualified electronic signatures (QES)?

Not yet. Remote signing through a qualified trust service provider with the CSC API is planned (VS-18).

Licence and use

Can I use OpenSeal in a commercial or closed-source product?

Yes. It is licensed under Apache-2.0: you may use, modify, embed, host and sell products built with it, with no royalties and no separate commercial licence. When you redistribute it, keep the LICENSE and the NOTICE file. See brand and attribution.

Do I have to show "Powered by OpenSeal"?

No. It is appreciated, never required, and OpenSeal never adds it to your application or your PDFs.

Why not use an existing open-source project?

The established open-source e-signature projects (DocuSeal, Documenso, OpenSign by OpenSign Labs, LibreSign) are licensed under the AGPL, which many companies cannot ship inside their products, and several keep features such as conditional fields, bulk send or SSO in paid editions. OpenSeal is permissively licensed and plans every feature for the open core. OpenSeal is written clean-room: no code from those projects is copied or adapted.

Evidence and verification

How can someone check a document without OpenSeal?

The sealed PDF is standard PAdES, so independent validators such as pyHanko and EU DSS check it, and OpenSeal's own verifier runs offline in a browser or on the command line. See Verifying a document.

What happens if the OpenSeal server disappears?

Every party already holds the sealed PDF with its certificate of completion and audit trail inside, protected by the seal and a trusted timestamp. Nothing needs the server to be verified.

Where are the signing keys kept?

In keyd, a separate service that uses your HSM through PKCS#11 and signs digests only. See Signing keys.

Integration

Is there an API?

Yes: a REST API under /api/v1, described in OpenAPI, with API keys and OAuth client credentials, idempotency keys, ETags for safe concurrent edits, and signed webhooks. See the API reference and Webhooks.

Is the API compatible with DocuSign's?

Its concepts are the familiar ones (envelopes, recipients, routing orders, fields, templates, embedded views). A DocuSign-shaped compatibility endpoint is a separate, later question, to be decided with counsel (VS-25).

Can I embed signing in my application?

An embedded signing link for a recipient is available through the API today. Embeddable signing and preparing elements are planned (VS-09).
